# Манюня

Telegram-бот: `/go` — материалы с Яндекс Диска, `STM` / `MTS` — поиск розеток и DMX в Google Sheets, `/id` — ID текущего чата, «чч» — цитаты для избранных. Новый обработчик автоматически проверяет фотографии авиационных и железнодорожных билетов в выбранных группах.

## Настройка

Python 3.12 или новее. Зависимости проверены по PyPI 23.09.2026; совместимость проверяется установкой `requirements.txt`.

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Создайте `.env` рядом с `main.py` по `.env.example`, не перезаписывая существующие настройки. Никому не отправляйте этот файл. Рабочий каталог при запуске — папка с `main.py`.

1. Сохраните существующие `BOT_TOKEN`, `YANDEX_TOKEN`, `ALLOWED_GROUP_IDS` и настройки Google Sheets.
2. Заполните `OPENAI_API_KEY` (нужны доступ к модели и средства API). По умолчанию используется vision-модель `gpt-5.6-sol` через Responses API со Structured Outputs; модель можно заменить через `TICKET_MODEL` на совместимую с изображениями и структурированными ответами.
3. `TICKET_RECIPIENT_ID` — числовой ID **одного** пользователя. Получите его командой `/id` в **личке** бота, не в группе. Получатель должен открыть личку и нажать Start; вводить паспорт в Telegram не нужно.
4. `TICKET_GROUP_IDS` — отрицательные ID рабочих групп через запятую. Они должны также входить в `ALLOWED_GROUP_IDS`. Получатель должен состоять в каждой группе, откуда ему пересылаются билеты; членство проверяется перед распознаванием и отправкой.
5. Заполните `TICKET_SURNAME`, `TICKET_GIVEN_NAME`, `TICKET_PATRONYMIC` точно по документу. Для авиабилетов задайте `TICKET_LATIN_SURNAME` и `TICKET_LATIN_GIVEN_NAME` точно как в загранпаспорте. Неточные варианты, инициалы и автоматическая транслитерация не используются. В `TICKET_PASSPORTS` укажите полные серию и номер; несколько документов разделите `;`. Пробелы и дефисы игнорируются, буквы и цифры не исправляются.
6. Чтобы бот видел обычные фотографии группы, назначьте его администратором либо отключите privacy mode через BotFather (`/setprivacy`; после изменения может потребоваться заново добавить бота). Для надёжного `getChatMember` других пользователей Telegram требует статус администратора. Сообщения других ботов могут быть недоступны. [Telegram FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get), [getChatMember](https://core.telegram.org/bots/api#getchatmember).
7. Поставьте `TICKETS_ENABLED=true`. После заполнения настроек самостоятельно запустите `.venv/bin/python main.py`. Пока функция выключена, новые ключи не требуются, прежние команды работают.

Распознавание целиком выполняет облачная модель; Локальные библиотеки проверяют форматы и визуализируют PDF, OCR на компьютере нет. Оплаченная подписка ChatGPT/Codex сама по себе не подтверждает наличие средств и доступа в API: для этого бота нужны отдельный API-ключ и настроенный API-биллинг. Проверьте их в своём аккаунте; бот не использует подписку приложения. [Создание API-ключа](https://developers.openai.com/api/docs/quickstart), [тарифы API](https://developers.openai.com/api/docs/pricing).

По выбору пользователя модель — `gpt-5.6-sol`, без автоматического переключения на дорогую модель. Запрос использует `reasoning.effort=medium` и общий предел 25 000 токенов на reasoning и структурированный ответ, согласно рекомендуемому начальному запасу для reasoning-моделей; предел не означает обязательный расход всех токенов. Незавершённый ответ не считается распознанным билетом. Совместимость проверена через SDK без платного вызова; качество на реальных билетах зависит от изображения. [Модель](https://developers.openai.com/api/docs/models/gpt-5.6-sol), [reasoning и лимит ответа](https://developers.openai.com/api/docs/guides/reasoning).

## Как проверяются билеты

Принимаются Telegram-фото, документы JPEG/PNG/WebP и PDF до 15 МБ. Изображения ограничены 25 млн пикселей, без анимации; HEIC, видео и прочие документы пропускаются. Элементы альбома обрабатываются независимо (до двух одновременно). Длинные пачки обрабатываются по мере освобождения обработчиков.

PDF — максимум 20 страниц: каждая страница визуализируется в памяти через PDFium, затем распознаётся облачным ИИ. Локального OCR нет. Из смешанного PDF отправляются только независимо опознанные страницы вашего билета, отдельными PDF-файлами. Чужие страницы не пересылаются. Выходной PDF — визуальная копия страницы до 300 dpi (до 9 млн пикселей), без скрытых объектов, вложений и соседних страниц исходного документа; это не исходный векторный/подписанный PDF. Страницы-продолжения без достаточных данных пассажира не привязываются по соседству и пропускаются. Страница или фото с несколькими пассажирами либо неоднозначной принадлежностью пропускается молча; автоматического вырезания отдельных билетов на одной странице нет. Зашифрованные, повреждённые и превышающие лимиты PDF не обрабатываются.

Для отправки достаточно точного полного документа **либо** точного ФИО; для авиабилета допустимо отсутствие отчества при точном имени и фамилии. Совпадение имени само по себе не исключает тёзку: сообщение говорит о совпадении данных, а не гарантированной идентификации. Если документ совпал, а ФИО отличается, билет доставляется с отметкой расхождения. Если ФИО совпало, а документ отличается/нечитаем/отсутствует, его статус указывается отдельно. Скрытые или неполные цифры не восстанавливаются. Прочие поля: «совпадает», «расхождение», «не удалось прочитать», «поле отсутствует». Общего «всё ок» нет.

В личку отправляется исходное фото/документ с компактной подписью: дата и время отправления, пункт отправления → пункт прибытия. Аэропорт/вокзал и город берутся только из билета, без выдуманных расшифровок кодов. Поездки туда, обратно и пересадки одного пассажира идут отдельными строками со своими датами и временем; отсутствующие/нечитаемые значения явно обозначаются.

Код бронирования и номер билета отправляются отдельными короткими сообщениями в копируемом формате, если прочитаны. Общие коды выводятся один раз; отдельные помечаются номером направления. В пределах одного PDF повторные одинаковые сообщения с кодами подавляются только в памяти. Внизу основной подписи: «Документ совпадает» либо короткий статус расхождения, отсутствия или невозможности чтения. Паспортный номер в подпись не добавляется. Локальная сверка ФИО сохранена; обычный список проверок скрыт, но обнаруженное расхождение ФИО отмечается одной строкой. Для редкого длинного маршрута, который не помещается в подпись Telegram, информация отправляется текстом сразу после оригинала без потери направлений.

Если ваш билет не найден или принадлежность не подтверждена, бот ничего не отправляет. По чужим, неоднозначным и нераспознанным билетам уведомлений нет. Ошибки также не вызывают сообщений в личку; в логах остаётся только общий технический маркер без содержимого. В группу бот результатов сверки не пишет. Подписи отправителя и инструкции на фото не управляют получателем или сверкой.

Для диагностики включены обезличенные этапы в отдельном логгере `tickets`: получение фото/документа, загрузка, начало/завершение API, причина пропуска и успешная отправка. `job` — счётчик обработки внутри процесса, не ID пользователя/чата/сообщения. Причины различают группу, членство, повтор, неподдерживаемый файл, неопределённость распознавания, несколько пассажиров и неподтверждённую принадлежность. Ошибки содержат только разрешённое имя типа, HTTP-статус и код из фиксированного списка, без текста исключения или ответа API. Содержимое билетов, ФИО, паспортные данные, маршруты, коды брони, имена файлов, Telegram ID и ключи в эти записи не включаются. `ticket_delivered` подтверждает отправку оригинала, `delivery_completed` — также подписи и кодов; отсутствие этих событий не означает успешной обработки.

## «Распознать, отправить и забыть»

Модуль не создаёт файлов, БД, постоянных кешей, журналов OCR или фото. Загрузка идёт в ограниченный буфер памяти, который закрывается и при ошибке. Распознанные поля существуют только в рамках обработки; исключения и их содержимое не журналируются. Эталон остаётся в `.env` и памяти, в запрос к ИИ он не включается. Не включайте отладочные HTTP-логи, дампы памяти и стороннее логирование запросов. Python/ОС не гарантируют криптографическое обнуление RAM или отсутствие системного swap.

Только пары `(chat_id, message_id)` хранятся в памяти 10 минут, максимум 2000 записей. Это подавляет повтор доставки одного обновления, включая ошибки отправки с неопределённым исходом. Новое сообщение, повторная загрузка того же фото, истечение TTL или перезапуск могут привести к повторному распознаванию и расходу API. Постоянной дедупликации намеренно нет. После ошибки проверьте личку перед повторной отправкой фото новым сообщением. Потерянные при выключении процесса задачи автоматически не восстанавливаются.

Запрос OpenAI использует `store=false`, без Files API, фонового режима и истории диалога. Это отключает сохранение объекта ответа, **но не означает полного отсутствия хранения у провайдера**: стандартные журналы контроля злоупотреблений могут содержать контент и храниться до 30 дней (с исключениями), а кеширование и проверки изображений имеют отдельные правила. Эталон не передаётся, однако паспортные данные, уже видимые на самой фотографии, получает провайдер. Билет остаётся в Telegram-группе и личке, согласно правилам Telegram. [Политика данных OpenAI](https://developers.openai.com/api/docs/guides/your-data).

[Vision API](https://developers.openai.com/api/docs/guides/images-vision) может ошибаться в мелком тексте и цифрах. Автоматическая сверка не заменяет проверки оригинала. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) гарантирует структуру ответа, а не правильность OCR.

## Локальные проверки без сети

```sh
.venv/bin/python -m unittest discover -s tests -v
```

Тесты используют вымышленные данные и подменённые Telegram/OpenAI клиенты. Реальный `.env`, билеты и платные API не нужны и не читаются.

## Контейнер

`Dockerfile` использует Python 3.14.7, устанавливает закреплённые зависимости и запускает приложение от UID/GID 10001. `.dockerignore` допускает только исходники, requirements, Dockerfile и один файл тестов: `.env`, история Git, локальные данные и кеши не входят даже в контекст сборки. В финальном образе нет тестов.

Перед публикацией проверьте тестовую стадию для целевой платформы, затем соберите стадию `runtime` с тем же исходным кодом. Пользователь подтвердил Docker Hub `chtotos/manunya_3.0` и сервер Intel/Ubuntu (`linux/amd64`); для имени без тега используется `latest`.

```sh
docker build --platform linux/amd64 --target test -t manunya:ticket-amd64-test .
docker build --platform linux/amd64 --target runtime -t chtotos/manunya_3.0:latest .
docker push chtotos/manunya_3.0:latest
```

Настройки передаются при запуске через `--env-file` или Compose `env_file`; не копируйте `.env` внутрь образа. Рабочая папка контейнера — `/app`. Бот работает через polling, входящие порты не нужны. Поддерживается обработка всей выбранной группы, без фильтра по теме.
